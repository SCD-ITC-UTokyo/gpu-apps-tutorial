nbody ビルドチュートリアル

3D N-body 重力多体問題 教材を、ビジュアル版で読むためのガイド

学べること 5 分で動かす ディレクトリ variant 命名 ビルド例 (stdpar) ビルド例 (Kokkos) configure.py 性能評価 エラー 困ったとき

このアプリで学べること

OpenMP 経験者が GPU プログラミングモデルを横断的に学べるよう、 同じ直接法 N-body 重力計算 (全粒子対の相互作用を O(N2) で評価) を 5 つの方式で実装しています。 各 impl は pragma 1〜3 行レベルの違い で済むようコードを揃えています。

方式C/C++Fortran特徴
OpenMP CPU✓ (C++)✓OpenMP の伝統的な CPU 並列。出発点
OpenMP target✓ (C++)✓omp target で GPU 化 (移行コスト最小)
OpenACC✓ (C++)✓acc kernels。NVIDIA 中心
言語標準 stdpar✓ (C++)—C++17 std::execution::par。pragma 不要
言語標準 do concurrent—✓Fortran 2008 do concurrent
Kokkos✓ (C++)—C++ ライブラリ。CPU/GPU portability

nbody は 全 variant が C++ コード (src/base/nbody.cpp の単一コンパイル単位 + src/common/*.hpp, src/util/*.hpp) です。ディレクトリ名 C++/ はそのまま C++ ソースを意味します (diffusion / fem では同じ C++/ に C コード .c が入りますが、nbody には .c はありません)。

教材スコープ: 精度は FP32 / FP64 と、その混合 (FP_L=32, FP_M=64) の 3 通り。 FP_H (保存量計算等) は常に FP64 固定です。FP16/BF16/tensor cores は対象外。

最短経路 (ローカル GPU で OpenMP target を動かす)

nbody ディレクトリに移動

bash
cd nbody

構成を生成 (CMake ファイルを作る)

bash
./configure.py --variant C++/openmp-target/auto.def --machine local --mode gpu

ビルドディレクトリに移動してビルド

bash
cd C++/openmp-target/auto.def
cmake -B build-local-gpu -S .
cmake --build build-local-gpu

実行 (BENCHMARK_MODE のオプション)

bash
./build-local-gpu/nbody.gpu.32.32 --num_min=1024 --num_max=65536 --num_bin=7

nbody は位置引数を取りません。BENCHMARK_MODE では粒子数を --num_min 〜 --num_max の間で --num_bin 点だけ対数刻みに振って測定します (引数なしなら既定 num_min=1024, num_max=4194304, num_bin=13, elapse_min=1.0)。

測定結果は標準出力ではなく log/<--file の値>_run.csv (既定 log/collapse_run.csv) に追記されます (9 カラム CSV、1 行目が列名):

output
exec,N,time[s],step,time_per_step[s],interactions_per_sec,Flop/s,FP_L,FP_M
./build-local-gpu/nbody.gpu.32.32,1024,8.621e-02,64,1.347e-03,7.784e+08,1.868e+10,32,32

うまく動いたら: ビルド方法 (stdpar 例) や ビルド方法 (Kokkos 例) でほかの実装を試しましょう。 動かない場合は 困ったとき へ。

variant 命名の意味

<lang>/<impl>/<variant> の階層 (Kokkos のみ 4 階層):

軸値意味
<lang>C++ (ディレクトリ名)C/C++ ソース (.c, .cpp) — C++ コンパイラで処理する言語ディレクトリ
FFortran ソース (.f90)
<impl>openmp-cpuOpenMP CPU マルチコア (ベースライン)
openmp-targetOpenMP target offloading (5.0+)
openaccOpenACC
stdparC++ 言語標準 (std::execution::par)
do-concurrentFortran 言語標準 (do concurrent)
kokkosKokkos (C++ のみ、4 階層命名)
<variant> (非 Kokkos)auto.def自動メモリ管理 (managed) + デフォルト並列度
auto.optmanaged + NTHREADS=128 (omp-target/openacc のみ実効)
manu.def手動メモリ管理 (separate)
manu.optseparate + NTHREADS=128
<policy>/<sub> (Kokkos)policy = range/mdrange/team、sub = baseline/uvm/cpu-tile-sweep 等

注: openmp-cpu は variant 階層を持たず (<lang>/openmp-cpu/src/ 直下にソース)、 stdpar と do-concurrent は auto.def / auto.opt のみ。

実行 (ジョブスクリプトを投入)

Miyabi はバッチジョブ専用 (PBS Pro)。configure.py が run.miyabi.uni.sh を 自動生成します。課金グループ (group_list) は id -gn の primary group が埋まるので、そのままで良ければ qsub するだけです (違う場合は --group で指定)。以下は実際に生成されるスクリプトの中身 (machine yaml の job: ブロックから組み立て):

run.miyabi.uni.sh (自動生成)
#!/bin/bash
# group_list: primary group (gz00) を自動検出。違う場合は --group で明示指定
#PBS -N "nbody"
# queue: 'debug-g' (machine yaml の job.per_mode.uni.queue。--queue で上書き可)
#PBS -q debug-g
#PBS -l select=1:ompthreads=72
#PBS -l walltime=00:10:00
#PBS -W group_list=gz00
#PBS -j oe

################################################################
# 環境設定: コンピュートノードは module 未ロード状態で起動します。
# ビルド時と同じ環境を再現してください (以下はこの machine の推奨例)。
# 必要に応じて編集 / コメントアウト解除して使ってください。
#
#   module purge
#   module load nvidia/25.9
################################################################

cd ${PBS_O_WORKDIR}
export OMP_PROC_BIND=spread
export OMP_PLACES=threads


# === 実行 ===
#   BENCHMARK_MODE では粒子数を対数的に振って測定する。
#   引数なしで既定値 (num_min=1024, num_max=4194304, num_bin=13,
#   elapse_min=1.0 [s]) が使われる。変更する場合は下のコメントを参照:
#     --num_min N --num_max N --num_bin N --elapse_min SEC --file NAME
#   使用可能なオプション一覧は --help で表示される。
./build-miyabi-uni/nbody.uni.32.32
bash
qsub run.miyabi.uni.sh         # ジョブ投入
qstat -u $USER                 # 状態確認
# 完了後、nbody.o<jobid> に標準出力が書き出される (#PBS -N "nbody" のため)

Wisteria の場合: スケジューラは PJM (Fujitsu)。ディレクティブは #PJM -L rscgrp=debug-a / #PJM -L node=1 / #PJM --omp thread=72 / #PJM -L elapse=00:10:00 / #PJM -g xxx / #PJM -j。課金グループは自動検出値が入ります。なお Wisteria は uni mode 非対応 (modes: [gpu, cpu]) なので、--mode gpu で生成した run.wisteria.gpu.sh を pjsub で投入します。状態確認は pjstat。

測定結果は log/collapse_run.csv に追記される 9 カラム CSV です (ジョブ出力 nbody.o<jobid> 側にはコンパイラ / ランタイムのメッセージが出ます):

Kokkos variant の選び方

名前policyメモリ特徴
range/baselineparallel_for (RangePolicy)default最もシンプル
range/cpu-sweepRangePolicydefaultcompile flag sweep 用
range/uvmRangePolicyCudaUVMSpaceUVM のオーバーヘッドを観察
range/uvm-sweepRangePolicyCudaUVMSpaceUVM + sweep
mdrange/baselineMDRangePolicydefaultbaseline (tile = default)
mdrange/cpu-tile-sweepMDRangePolicydefault_NX/_NY/_NZ マクロ
mdrange/uvmMDRangePolicyCudaUVMSpace—
mdrange/uvm-tile-sweepMDRangePolicyCudaUVMSpaceUVM + tile
team/baselineTeamPolicy + TeamThreadRangedefaultchunk = 32 ハードコード
team/cpu-chunk-sweepTeamPolicydefault_CHUNK マクロ
team/uvmTeamPolicyCudaUVMSpace—
team/uvm-chunk-sweepTeamPolicyCudaUVMSpaceUVM + chunk

RangePolicy について: range/* の各 variant のソースには RangePolicy という文字列は現れず、Kokkos::parallel_for("calc_acc", Ni, ...) のようにループ長 (整数の i 粒子数 Ni) を直接渡しています。これでも実体はディレクトリ名どおり RangePolicy です — Kokkos は整数の extent を受け取ると内部で Kokkos::RangePolicy<>(0, Ni) に暗黙変換します (parallel_for(N, f) ≡ parallel_for(RangePolicy<>(0, N), f))。mdrange の MDRangePolicy や team の TeamPolicy を明示構築するのと対照的に、これは「ポリシーを明示的に書かない最短記法」です。

注: UVM variant は GPU mode (または uni) 必須 (CudaUVMSpace は CUDA backend 要)。 --mode cpu で UVM variant を指定すると configure.py がエラー終了します。

tile / chunk sweep の例

bash
# tile sweep 例 (Kokkos mdrange)
./configure.py --variant C++/kokkos/mdrange/cpu-tile-sweep --machine miyabi --mode gpu \
    --tile-nx 4 --tile-ny 8 --tile-nz 64
cd C++/kokkos/mdrange/cpu-tile-sweep
cmake -B build-miyabi-gpu -S . && cmake --build build-miyabi-gpu

# chunk sweep 例 (Kokkos team)
./configure.py --variant C++/kokkos/team/cpu-chunk-sweep --machine miyabi --mode gpu --chunk 128
cd C++/kokkos/team/cpu-chunk-sweep
cmake -B build-miyabi-gpu -S . && cmake --build build-miyabi-gpu

configure.py の使い方

configure.py は variant / machine / mode を受け取って variant ディレクトリに 2 種のファイルを生成します:

  1. ビルドファイル: CMakeLists.txt (default) または Makefile.gen.<machine>.<mode>
  2. ジョブスクリプト run.<machine>.<mode>.sh — machine yaml の job: ブロックから自動生成 (Miyabi → PBS Pro qsub、Wisteria → PJM pjsub、local → 直接 bash)

--groupnostrジョブスクリプトの課金グループ (PBS group_list / PJM -g)。省略時は id -gn で自動取得
--kokkos-rootnostrKokkos の install prefix。省略時は machine yaml の kokkos.root を使い、それが placeholder のときだけ Kokkos_ROOT/KOKKOS_ROOT、CMAKE_PREFIX_PATH、~/kokkos/* 等から自動検出。見つからない場合は指定を促して終了
--queuenostrジョブスクリプトの投入キュー (PBS -q / PJM -L rscgrp)。省略時は machine yaml の job.per_mode.<mode>.queue。scheduler: none の machine (local) に渡すと ERROR
--dry-runno—ビルドファイルの生成内容を stdout 表示 (書き込まない)
--dry-jobno—ジョブスクリプトの生成内容を stdout 表示 (--dry-run と併用で両方)
--cleanno—生成物を削除 (実行結果 log/ と results/ は残す)。--variant/--machine/--mode で対象を絞れる
--allcleanno—--clean に加えて log/ も削除 (results/ は残す)
--yes, -yno—--clean/--allclean の確認プロンプトを省略 (非対話環境では必須)

オプションと variant の対応 (重要)

--nthreads / --tile-nx/ny/nz / --chunk は対応しない variant を指定すると ERROR で拒否されます (静かに無視はしません)。 --opt-level / --extra-cflags は Kokkos variant でも受理され、生成 CMakeLists の target_compile_options としてアプリのコンパイル単位にのみ適用されます (Kokkos ライブラリ本体はインストール時の設定のまま)。

オプション非 KokkosKokkos

--nthreads✓ auto.opt/manu.opt の omp-target/openacc のみ✗
--tile-nx/ny/nz✗✓ mdrange/*-tile-sweep のみ
--chunk✗✓ team/*-chunk-sweep のみ
--opt-level✓ 全 variant (ベースフラグを置換)△ アプリ TU にのみ target_compile_options として適用 (Kokkos 本体はインストール時の設定)

CLI オプション例 (精度・最適化を直接指定)

各例ごとにコピーボタンを用意しています。

倍精度 (FP_L=FP_M=64) でビルド構成生成  → バイナリ名: nbody.gpu.64.64

bash
./configure.py --variant C++/openmp-target/auto.def --machine local --mode gpu --fp 64

NTHREADS=256 を default に  → バイナリ名: nbody.gpu.32.32.256

bash
./configure.py --variant C++/openacc/auto.opt --machine local --mode gpu --nthreads 256

倍精度 + NTHREADS の組み合わせ  → バイナリ名: nbody.gpu.64.64.256

bash
./configure.py --variant C++/openmp-target/auto.opt --machine local --mode gpu --fp 64 --nthreads 256

Kokkos tile sweep のデフォルト tile size を指定

bash
./configure.py --variant C++/kokkos/mdrange/cpu-tile-sweep --machine local --mode gpu \
    --tile-nx 4 --tile-ny 8 --tile-nz 64

Kokkos chunk sweep のデフォルト chunk size

bash
./configure.py --variant C++/kokkos/team/cpu-chunk-sweep --machine local --mode gpu --chunk 256

ベース最適化レベルを変更  (default: machine yaml の -O3)

bash
./configure.py --variant C++/openmp-target/auto.def --machine local --mode gpu --opt-level fast

arch / vector ext 等の任意フラグを追加

bash
./configure.py --variant C++/openacc/auto.def --machine miyabi --mode cpu --compiler intel \
    --opt-level O3 --extra-cflags="-march=sapphirerapids -funroll-loops"

machine 情報の自動検出 (local のみ)

--machine local 指定時は、実行ホストから OS / CPU / GPU / NVHPC バージョンを自動検出して表示します。 リモート機 (miyabi, wisteria) は yaml の description を使用 (ローカルから検出できないため)。

bash
cmake -B build-local-gpu-fp64 -S . -DFP_L=64 -DFP_M=64

./build-local-gpu-fp64/nbody.gpu.64.64 --num_min=65536 --num_max=65536 --num_bin=1
GPU が認識されない / 遅すぎる
bash
# GPU 認識確認
nvidia-smi

N が小さすぎると GPU を使い切れず CPU より遅いこともある。--num_min を大きくして再評価する。

Kokkos の警告 compute capability ... reduce performance

Kokkos インストール時の GPU arch と実機の arch が違う場合の警告。動作はする (互換モード)。気になる場合は Kokkos を実機の arch に合わせて再インストール:

bash
# 例: Blackwell (sm_120) 向け
spack install kokkos +cuda +openmp +wrapper cuda_arch=120 cxxstd=20
stdpar / do-concurrent が GPU で動かない (will run sequentially when compiled for a compute capability less than cc70)

-stdpar=gpu を付けていても、compute capability を明示しないと nvc++ / nvfortran はコンパイル時のホストで既定の cc を選ぶ。GPU の無いログインノードでビルドすると cc70 未満になり、std::execution::par / do concurrent は警告だけ出して逐次コードに退化する (エラーにならないので気付きにくい)。

machine yaml の gpu.common_flags に実機の arch を入れる。machines/wisteria.yaml は Aquarius = A100 なので -gpu=cc80 を指定済み。

yaml
gpu:
  common_flags: ["-tp=native", "-gpu=cc80", "-O3", "-I.", "-Wall", "-Minfo=accel,opt,mp"]

ビルドログに上記の警告が残っていないことで確認できる。

error: global or namespace scope variables ... cannot be accessed from device code

stdpar でオフロードを有効にしたときに出る。C++ のラムダはグローバル変数をキャプチャしないため、ファイルスコープの変数をラムダ内から参照するとデバイス側に渡らない。ラムダの外でローカル変数に束縛し直し、[&] ではなく [=] で値キャプチャする。要素ごとの作業配列をファイルスコープに置いている場合は、並列化するとデータ競合になるのでラムダ内のローカル変数にする。

compiler 'intel' は machine 'wisteria' に定義されていない

エラーメッセージに使用可能な選択肢が表示される。指示通り --compiler gcc 等で再実行。
